# Repository Guidelines

## Project Scale

This is a Minecraft plugin, not a multimillion-dollar enterprise project. Keep it solid, reliable, and maintainable, but do not overengineer it.

Prefer the simplest change that solves the actual problem, follow existing patterns, and test behavior that matters. Avoid speculative abstractions, unnecessary compatibility layers, excessive defensive code, and process overhead unless a concrete requirement justifies them. Apply extra care where mistakes could duplicate or lose items, affect the economy, corrupt configuration, or destabilize the server.

Do not write design specs or implementation plans for small, straightforward changes. Only do so when the user explicitly asks or the work is complex enough to genuinely benefit from one.

## Issue Tracking (Plane)

Plane is the source of truth for issue tracking in this repository. This repository uses the Plane project `AIRDR` (Airdrop).

- Do not use or recreate `issues.md` for active tracking.
- Track all new work in Plane work items and use the Plane work item identifier in related development artifacts.

### Tagging Work Items in PRs and Commits

- PRs: include the Plane work item key in the PR title or body (for example `AIRDR-123`).
- PRs: when applicable, use closing/reference keywords in the PR description, such as `Closes AIRDR-123` or `Refs AIRDR-123`.
- Commits: include the Plane work item key in the commit subject or body (for example `AIRDR-123: improve package drop validation`).
- Commits: when a commit directly resolves the work item without follow-up, include a closing reference such as `Closes AIRDR-123`.

## Project Structure & Module Organization
- `src/main/java/com/airdropmc` holds the plugin code, grouped by feature area: `commands/`, `controllers/`, `listeners/`, `packages/`, `tasks/`, `events/`, `config/`, `helpers/`, and `exceptions/`.
- `src/main/resources` contains shipped configs (`config.yml`, `packages.yml`). These are copied to the server at runtime.
- `build/` is the Gradle output location (JARs in `build/libs/`).
- `gradle/` and `gradlew*` are the Gradle wrapper; `readme/` stores README assets.

## Build, Test, and Development Commands
- `./gradlew clean build` builds the plugin JAR and generates `plugin.yml` into the artifact.
- `./gradlew test` runs JUnit Jupiter tests.
- `./gradlew runServer` starts a local Paper test server and drops the built plugin into `plugins/`.

## Coding Style & Naming Conventions
- Java 21, Paper API, UTF-8. Match existing formatting: tabs for indentation, braces on the same line.
- Packages live under `com.airdropmc`; keep feature folders aligned with `src/main/java`.
- Class naming patterns used throughout: `*Controller`, `*Listener`, `*Gui`, `*Config`, `*Exception` (e.g., `DropController`, `CrateOpenListener`).
- Do not add a static `plugin.yml`; it is generated by Gradle from `build.gradle.kts`.

## Testing Guidelines
- Tests use JUnit 5. Place them in `src/test/java` mirroring production packages.
- Prefer `*Test` class names and keep unit tests focused on controller and package logic.
- Run `./gradlew test` before submitting changes that alter behavior.

### LightKeeper tests

- Add `*IT` classes under `lightkeeper/src/test/java/com/airdropmc/integration` to exactly one CI shard.
- Share the class server; reserve `@FreshServer` for boot isolation. Use unique worlds/bots. In `finally`, restore files/providers, settle holds, clean crates, remove bots, and close captures.
- Reuse setup helpers and batch server calls. Await correlated state/events and completed reloads. Synthetic GUI clicks do not prove native inventory transfers.
- Use Java 21: `./gradlew lightkeeperTest`; focus with `lightkeeperScenarioTest -PlightkeeperTests=ClassIT`. Verify changed method order when sharing state.

## Commit & Pull Request Guidelines
- Recent commits are short, lowercase, and task-focused (e.g., "set version to 3.3", "default smoke effect to off"); keep subject lines concise.
- PRs should include a brief summary, testing notes (`./gradlew test` or `./gradlew runServer`), and call out any config changes to `config.yml` or `packages.yml`.

## Configuration & Dependencies
- Runtime dependencies: LuckPerms, EssentialsX, Vault (ensure they’re installed on the server).
- Update defaults in `src/main/resources/config.yml` or `src/main/resources/packages.yml` and document behavioral changes in the PR.
